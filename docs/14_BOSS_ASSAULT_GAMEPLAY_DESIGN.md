## 0. 문서의 효력과 용어

이 문서는 기존 게임을 보존하면서 새로운 진행 방식을 개발하기 위한 계약 초안이다. 기존 GDD, 승인된 카드, HANDOVER의 SSOT 로드맵을 자동으로 대체하거나 전진시키지 않는다.

| 표시 | 의미 |
|---|---|
| 요구사항 | 사용자 대화에서 확인된 개편 방향 |
| 설계안 | 요구사항을 충족하기 위한 제안. 카드 승인 시 적용 범위를 확정 |
| 검증값 | 시제품에서 시험할 숫자. 확정 밸런스가 아님 |
| 미확정 | 후속 결정이 필요하며 임의 구현하지 않을 항목 |

`legacy`는 현행 게임, `boss_assault`는 신규 게임 방식의 가칭이다. 타입·상태·파일명 역시 별도 표시가 없으면 제안명이며 현재 존재하는 API라는 뜻이 아니다.

## 1. 목적과 핵심 요구사항

### 1.1 목적

기존의 문제 러닝, 단일 답 선택, 정답 별 수집/오답 회피 분기를 보스의 연속 공격에 대응하는 흐름으로 바꾼다. 수학을 생각할 시간을 확보하면서 타격과 전신 운동의 연결감을 높인다.

### 1.2 요구사항

1. 전면 보스가 문제를 강하게 던지는 연출로 라운드를 시작한다.
2. 문제에 대해 생각할 시간은 기본적으로 최소 8박을 보장한다.
3. 보스 양손에서 답 두 개가 날아오며 플레이어가 하나를 펀치한다.
4. 한 문제 안에서 서로 다른 보기 쌍이 반복해서 등장할 수 있다.
5. 답 펀치와 스쿼트 회피 공격을 번갈아 수행한다.
6. 정답이면 해당 답 공격이 무효화되고, 오답이면 공격이 도착하여 플레이어 HP가 감소한다.
7. 정답·오답 후 별도의 운동 페이즈로 분기하지 않는다.
8. 보스에게 접근한 뒤 펀치·피하기·점프 등을 조합한 근접 결전을 진행한다.
9. 정답 타격 수를 결과에 활용하고, 추후 목표값과 같은 수식을 고르는 문제로 확장한다.

### 1.3 비목표

- 이번 문서 작성으로 소스 코드, CSV 원본, 기존 밸런스, 저장 기록을 변경하지 않는다.
- 모든 챕터의 신규 공격 패턴과 수식형 출제를 한 번에 구현하지 않는다.
- 기존 카메라·아바타·스켈레톤·편집기를 전면 재작성하지 않는다.
- 온라인 순위 서버, 부정행위 방지, 새 에셋 제작 전체는 본 설계의 초기 범위가 아니다.

## 2. 현행 구현과 충돌 지점

### 2.1 코드 확인 기준

다음은 설계 조사 시점의 코드 기준이다. 구현 착수 전 대상 파일을 다시 확인한다. 과거 문서와 차이가 있다는 이유만으로 현행 동작을 임의 수정하지 않는다.

| 근거 파일: `dream_guardian/` 기준 | 확인 내용 | 신규 방식의 대응 |
|---|---|---|
| `src/game/BeatRunCoordinator.ts` | 문제당 답 선택 1회, 정답/오답 분기, 선택 후 rest 처리 | 반복 공격 전용 컨트롤러 분리 |
| `src/game/BeatRoundResolver.ts` | 라운드 결과가 correct/wrong/timeout 중 하나이며 보상과 통계를 변경 | 다중 답 결과를 받는 신규 정산 계약 |
| `src/game/BattleState.ts` | HP·마나·기존 정답 통계 보유, 자원 메서드 자체에는 공격 ID 중복 차단 없음 | HP 저장 재사용, 신규 정산 경로에서 중복 차단 |
| `src/game/StageProgressController.ts` | 완료 라운드·사망 우선·결전 인계 관리 | 원칙 재사용, 기존 단일 답 결과와의 결합은 어댑터 검토 |
| `src/core/AppBootstrap.ts` | 상태 진입·입력·정산 연결 및 기존 결전 시스템 자동 시작 | 모드별 실행과 종료를 배타적으로 구성 |
| `src/core/SceneDirector.ts` | 모션 처리와 여러 게임 컨트롤러의 update/render 연결 | 공통 입력 획득과 모드별 게임 실행 분리 |
| `src/input/ArmReachAnswerSelector.ts` | 팔 뻗기 선택 및 한 번 확정 | 손 회수 후 재타격 보장을 추가 검증 |
| `src/motion/MotionIntentBus.ts` | 스쿼트 의도 처리 존재 | 좌표 단위·기준점·복귀 판정을 검증한 뒤 사용 |
| `src/game/MotionNoteTimeline.ts` | 다중 노트와 판정기 등록, load 시 초기화 | 재사용 가능하나 답 두 개를 독립 필수 노트로 취급하지 않음 |
| `src/render/MotionNoteRenderer.ts` | 공용 투영·노트 렌더링 | 답 라벨과 쌍 단위 무효화 표현 확장 |

### 2.2 밸런스 및 문서 차이

- `config/battle.config.ts`의 현재 기본값은 플레이어 HP 100, 일반 보스 HP 500, 최종 보스 HP 750, Phase A 10문제이다.
- 같은 설정의 정답 마나 보상은 25, 스펠 비용은 100이며, 이 수치는 신규 타격마다 그대로 적용하지 않는다.
- `BeatRoundResolver`의 기본 nonLethalPhaseA 경로는 스펠을 처리하더라도 보스 HP 피해를 차단한다.
- 이전 GDD의 보스 HP 10/20 및 Phase A 스펠 피해 설명과 차이가 있다. 문서 정합성 갱신은 별도 승인 범위로 다룬다.
- 현행 결과 저장은 정답 문제 수에 의존한다. 반복 타격 수를 넣으면 기존 점수의 의미가 바뀐다.

### 2.3 조사 한계

위 내용은 코드 읽기를 통한 조사이며 실기기 성능, 펀치 인식률, 스쿼트 결함을 재현한 결과가 아니다. 의심 지점은 검증 과제로 분리하고, 실제 버그가 확인되면 원인·수정 계획을 갖춘 카드로 등록한다.

## 3. 기존 게임 보존 및 실행 격리

### 3.1 세션 단위 모드 선택

- `legacy`를 개발 중 기본값으로 유지한다.
- `boss_assault`는 명시적인 내부 테스트 진입 경로로 실행한다.
- 세션 시작 시 모드를 고정한다. 모드 전환은 현재 세션 종료 후에만 허용한다.
- 신규 흐름 검증과 전환 승인 전에는 기존 메뉴의 기본 플레이를 바꾸지 않는다.
- 실행 중 문제가 생겼다고 같은 세션을 legacy로 이어 붙이지 않는다. 종료 후 기존 방식으로 새로 시작한다.

### 3.2 배타 실행 계약

| 경로 | 신규 모드의 금지 사항 |
|---|---|
| Update | 기존 BeatRunCoordinator, 별 수집, 기존 오답 회피의 동시 실행 |
| 입력 | 하나의 웹캠·키보드·터치 입력을 기존/신규 양쪽에 전달 |
| 정산 | 기존 onAnswerConfirmed 또는 resolver 콜백으로 신규 라운드 보상 지급 |
| 화면 | 기존 답 선택·별 수집·오답 분기 화면을 신규 공격 위에 중복 표시 |
| 결전 | 기존 BossFeverController, BossHazardController, 미니언 자동 포격의 자동 시작 |
| 종료 | 이전 모드의 예약 작업·구독·입력 버퍼를 다음 세션에 유지 |

단순히 기존 화면을 숨기는 것으로 격리를 완료했다고 판단하지 않는다. 보이지 않는 컨트롤러의 피해·보상·상태 전환 호출도 0회여야 한다.

## 4. 라운드 및 상태 계약

### 4.1 계층

```text
세션
  라운드: 문제 하나
    문제 투척
    생각 시간
    답 공격 1: 보기 두 개
    스쿼트 공격 1
    답 공격 2: 새 보기 두 개
    스쿼트 공격 2
    ... 설정된 공격 종료
    라운드 정산 1회
  다음 라운드 또는 근접 결전
```

답 공격 완료는 라운드 완료가 아니다. 문제 하나에서 정답 2회·오답 1회가 발생해도 완료 문제 수는 1만 증가한다.

### 4.2 상태 구조 설계안

```text
기존 준비/카운트다운
  -> ASSAULT_ROUND
       QUESTION_THROW -> THINK
       -> ANSWER_PAIR -> SQUAT_ATTACK -> ...
  -> ROUND_RESOLVE
       -> ASSAULT_ROUND 또는 BOSS_CLIMAX
  -> RESULT / GAMEOVER
```

- 신규 바깥 상태 `ASSAULT_ROUND`의 세부 진행은 전용 game 컨트롤러가 소유한다.
- 기존 상태 머신의 전환 표는 유지하고 신규 상태의 진입·정산·사망·종료 경로만 명시적으로 추가한다.
- 기존 STAR_COLLECT와 HAZARD_EVADE를 반복 왕복하는 방식으로 구현하지 않는다.
- ROUND_RESOLVE/BOSS_CLIMAX 재사용 시 진입 콜백은 모드별로 분리한다.
- HP 0은 라운드 중에도 즉시 종료 사유이다. 완료하지 않은 라운드를 완료 문제로 세지 않는다.
- RESULT/GAMEOVER 확정은 세션당 한 소유자가 한 번만 수행한다.

## 5. 시간 및 입력 경계 계약

### 5.1 문제 등장과 8박

1. 질문 데이터를 한 번 생성하고 투척 연출을 시작한다.
2. 연출 정의의 readable 시점에 문제를 안정된 위치·크기로 표시한다.
3. 그 시점부터 최소 8개의 완전한 활성 박자를 보장한다.
4. 문제 유형의 최소 읽기 시간이 더 길면 그 시간을 적용한다.
5. 조건 충족 이후 박자 경계에서 첫 답 공격을 시작한다.

`THINK`의 시작은 실제 렌더러의 draw 횟수나 애니메이션 콜백에 종속시키지 않는다. 게임이 표시 단계를 소유하고 렌더러가 같은 시간 정보를 소비한다. 프레임 정지·추적 상실 등으로 정상 표시를 보장할 수 없을 때의 안전 정지 정책은 별도로 적용한다. 탭 비활성화나 안전 기준을 넘는 프레임 정지 시간은 읽기 시간으로 소급 인정하지 않으며, 복귀 프레임의 시간 보정만으로 생각 구간이 끝나지 않게 한다. 안전 정지 임계값은 설정 카드에서 확정한다.

```text
필요 생각 시간 = max(8 * secondsPerBeat, 문제 유형별 최소 읽기 시간)
```

- 투척 애니메이션은 생각 시간에서 제외한다.
- 생각 중 피해 공격·정밀 펀치·스쿼트를 요구하지 않는다.
- 신규 기본안에서는 발걸음이 생각 타이머의 진행 조건이 아니다. 발걸음은 선택 운동으로 기록한다.
- 문제는 공격 중에도 계속 표시한다.
- TTS는 문제당 1회만 요청한다. 사용 중인 TTS가 더 길면 제한된 대기 후 다음 박자에서 시작하는 정책을 검토한다.
- TTS 비활성·실패 시 시간 계약만으로 진행한다. TTS 최대 대기값은 구현 전 확정한다.
- v0.3: 현행 `QuestionSpeech.status`는 3초 안전 타임아웃으로 발화 중에도 idle이 될 수 있다. 상태 관찰 대신 §15.2-B3의 시간 기반 정책을 기본안으로 한다. 문제 유형별 최소 읽기 시간은 §15.3-C1 분류 규칙으로 산출한다.

### 5.2 초기 검증 시퀀스

| 구간 | 검증값 | 내용 |
|---|---:|---|
| 투척 | 별도 설정 | 문제 등장·고정 |
| 생각 | 최소 8박 | 읽기·계산, 선택적 발걸음 |
| 답 공격 1 | 4박 | 발사·판정·도착·복귀 |
| 스쿼트 1 | 4박 | 예고·회피·복귀 |
| 답 공격 2 | 4박 | 새로운 보기 쌍 |
| 스쿼트 2 | 4박 | 두 번째 회피 |
| 정산 | 별도 정지 화면 없음 | 결과 반영·접근 표현 |

이 표는 시제품 값이다. 공격 내 선택창의 시작/끝, 도착 시각, 복귀 시간은 설정에서 분리하며 카드 승인 전 수치를 확정한다. 기존 2박 답 선택 쉼표 및 다음 라운드 지연을 중복 추가하지 않는다.

초기 BPM 후보는 100이며 8박은 4.8초이다. BPM 120에서는 4초이므로 BPM만 바꾸어 읽기 시간이 무조건 줄어들지 않게 최소 읽기 시간을 병행한다.

앞선 대화의 후보였던 8박 4타는 현재 교대형의 추가 확정 요구사항이 아니다. 8박 4타와 펀치/스쿼트 교대는 같은 운동 밀도가 아니므로, 빠른 프로필에서는 펀치 구간 내 두 쌍 배치를 시험하되 스쿼트 복귀 시간을 무리하게 줄이지 않는다.

### 5.3 공통 시계와 처리 순서

- 신규 게임 시간은 일시정지 구간을 제외한 활성 시간 하나로 통일한다.
- 입력 타임스탬프도 같은 시간축으로 변환한다. performance.now와 engine.elapsedTime을 직접 비교하지 않는다.
- 공격·복귀·다음 라운드 예약에 일반 setTimeout을 사용하지 않는다.
- 프레임 누락 시 지난 논리적 경계를 시간순으로 처리하고, 새 공격에 과거 입력을 재사용하지 않는다.
- 판정창 끝과 정확히 같은 시각의 유효 입력은 만료보다 먼저 처리한다.
- 입력과 경계 이벤트를 합쳐 시간순으로 처리한다. 입력 우선 규칙은 같은 시각에만 적용하며, 늦게 수집한 이후 시각의 입력이 앞선 마감보다 먼저 처리되지는 않는다.

```text
입력 수집/시간 정규화
 -> 유효 입력 판정
 -> 선택창 만료/공격 도착
 -> 피해와 결과 반영
 -> 사망 확인
 -> 다음 공격/라운드/결전 전환
```

일시정지 중 입력은 폐기한다. 카메라 추적 상실 시 안전 정지 후 자세 재준비를 요구하는 방식을 기본 제안으로 하며, 유예 시간은 미확정이다. 폴백 모드에서는 카메라 추적 여부로 게임을 정지시키지 않는다.

## 6. 데이터와 소유권

### 6.1 식별자

| 필드 | 의미 |
|---|---|
| sessionId | 재시작·모드 전환을 구분하는 세션 식별자 |
| roundId | 문제 하나의 생명주기 |
| pairId | 좌우 보기 한 쌍 |
| attackId | 피해 또는 회피를 정산하는 공격 |
| inputId | 한 번의 실제/폴백 동작 |
| rulesVersion / profileId | 적용한 규칙 및 난이도 설정 |

식별자는 세션 범위를 포함하거나 세션과 함께 검증한다. 피해 중복 차단 키는 예를 들어 `(sessionId, attackId, effectType)`처럼 부작용 종류까지 구분한다.

### 6.2 데이터 구분

- **정의**: 문제 참조, 보기 두 개, 정답 쪽, 공격 순서, 발사·입력창·도착 시각. 생성 후 불변이다.
- **런타임**: 현재 세부 상태, 선택 잠금, 공격 무효화, 적용된 결과 ID 집합.
- **결과**: 선택 정오, 미선택, 리듬 등급, 회피 성공, 실제 피해량, 중단 여부.
- **표시 스냅샷**: 문제 텍스트, 보기 텍스트, 투영 기준, 연출 상태, HUD 숫자. 정답을 렌더러가 추론하지 않는다.

### 6.3 책임 분리

| 레이어 | 책임 | 하지 않을 일 |
|---|---|---|
| Question | CSV 문제 공급·정답 평가·보기 구성 | HP·진행도 변경 |
| Motion/Input | 준비/회수 판정과 시각이 있는 동작 이벤트 | 정답 판정·보상 지급 |
| Game 진행 | 시퀀스·선택·공격 상태·라운드 생명주기 | 직접 Canvas 그리기 |
| Game 정산 | 피해·보상 적용 및 중복 차단 | 모션 임계값 계산 |
| Core 연결 | 모드별 수명주기·공통 시계·배타 실행 | 수학 평가 재구현 |
| Render/UI | 읽기 전용 상태 표시 | 선택 확정·HP 변경 |
| Config | 시간·피해·난도·표현 수치 | 런타임 상태 보관 |

기존 이벤트 인프라를 재사용하며 신규 전역 이벤트 버스를 추가하지 않는다.

### 6.4 데이터·설정·로직의 물리적 분리

다음 디렉터리는 제안 경계이며, 실제 신규 파일은 작업 카드의 허용 목록으로 확정한다. TypeScript 데이터 파일을 사용하더라도 함수·콜백·런타임 변경을 넣지 않는다.

| 종류 | 제안 위치: `dream_guardian/` 기준 | 담을 내용 | 넣지 않을 내용 |
|---|---|---|---|
| 구조 계약 | `src/types/assault*.ts` | 모드, 정의, 결과, 스냅샷, 버전 타입 | 기본 밸런스, 실행 함수 |
| 조정값 | `config/assault*.config.ts` | 읽기 시간, 입력창, 피해, 모션 임계값, 비주얼 수치 | 문제 텍스트, 패턴 실행 순서, 진행 상태 |
| 공격 콘텐츠 | `src/data/assault/` | 패턴 ID, 공격 종류와 순서, 박자 배치, 프로필 참조 | HP 변경, 조건 함수, 타이머, 정답 평가 |
| 수학 원본 | 기존 CSV 공급 경로 | 기존 문제 데이터와 향후 별도 승인된 확장 데이터 | 공격 피해·시각 효과 |
| 검증·해석 | `src/game/assault/` 등 책임별 레이어 | 데이터 검증, 시간표 컴파일, 진행·판정 | 챕터별 하드코딩 분기와 내장 패턴 목록 |
| 입력 해석 | `src/motion/`, `src/input/` | 좌표 정규화, 회수·복귀 상태, 이벤트 생성 | 정답값, 피해량, 보상 정책 |
| 화면 | `src/render/`, `src/ui/` | 스냅샷 기반 투영·표시 | 패턴 선택, 정답 판정, HP 변경 |

**설정은 얼마만큼, 콘텐츠는 무엇을 어떤 순서로, 로직은 어떻게 실행하는지를 담당한다.** 새 챕터나 패턴을 추가할 때 판정 코드에 bossId/chapter별 분기가 필요하면 분리 경계를 다시 검토한다.

### 6.5 선언형 콘텐츠와 시간표 컴파일

공격 콘텐츠는 예를 들어 다음 필드로 표현한다. 이는 스키마의 설명이지 현재 로더가 지원하는 파일 형식이라는 뜻은 아니다.

```text
schemaVersion, id, questionMode, timingProfileId, balanceProfileId
encounters[]:
  id, kind(answer_pair | squat | ...), startBeat, durationBeats,
  interactionProfileId, visualProfileId, answerPolicyId(답 공격만)
```

- 박자 인덱스는 신규 콘텐츠에서 0-based로 통일하고 기존 노트의 1-based 계약과 변환 경계를 명시한다.
- 시간 수치의 단위는 필드명에 Beats/Seconds/Ms로 표시한다. 단위 없는 duration/window를 금지한다.
- 질문·보기 표시값은 Question 레이어가 공급한다. 공격 패턴 데이터에 같은 정답 숫자를 다시 복사하지 않는다.
- 원본 데이터 -> 스키마/참조 검증 -> 선택 프로필과 결합 -> 불변 실행 계획의 순서로 처리한다.
- 실행 계획 생성 시 BPM과 프로필 버전을 고정한다. 프레임마다 전역 config를 다시 읽지 않는다.
- 판정창·도착·복귀가 슬롯 범위에 들어가는지, 필요한 복귀 간격이 확보되는지 사전 검증한다.
- 초기 버전은 한 번에 하나의 선택/회피 창만 활성화한다. 중첩 콘텐츠는 자동 보정하지 않고 검증 오류로 거부한다.
- 알 수 없는 schemaVersion/kind/profileId, 중복 ID, 음수·NaN·무한 수치, 순서 역전은 실행 전에 거부한다.
- 검증 실패 시 자원을 변경하거나 부분 세션을 시작하지 않는다. 이전 모드로 몰래 전환하지 않고 진입 화면에 오류를 알린다.

판정 로직은 검증된 계획을 소비한다. 콘텐츠에 eval, 실행 가능한 수식 문자열, 사용자 콜백 또는 JS 코드를 넣어 공격 행동을 확장하지 않는다. 수학 수식은 기존 안전 평가 경로만 사용한다.

### 6.6 순수 판정과 부작용 분리

```text
불변 계획 + 이전 상태 + 현재 게임 시각 + 입력 이벤트
  -> 판정/전이 결과
  -> 정산 명령(공격 ID, 대상, 결과 종류)
  -> 중복 차단 정산기
  -> 기존 HP 저장 객체 / 신규 통계
  -> 읽기 전용 화면 스냅샷
```

- 가능하면 판정·시간표 컴파일을 순수 함수 또는 외부 부작용 없는 객체로 테스트한다.
- 피해량은 선택된 balanceProfile에서 정산기가 해석한다. 입력 이벤트와 렌더러가 임의 피해량을 전달하지 않는다.
- 무작위 보기/패턴은 주입된 시드 소스로 생성한다. Date.now/Math.random을 판정 경로에 직접 숨기지 않는다.
- 불변 정의를 런타임 상태 저장소로 사용하지 않는다. 세션 reset은 상태·구독·버퍼만 비우고 원본 콘텐츠를 변경하지 않는다.
- 도메인 로직은 DOM, Canvas, localStorage, 네트워크, 실제 타이머를 직접 호출하지 않는다.

### 6.7 데이터 변경과 규칙 변경의 구분

- BPM, 피해량, 표시 색상, 기존 동작의 순서 조정은 데이터/config 카드로 다룬다.
- 새로운 동작 종류, 새로운 판정 의미, 새로운 보상 계산은 로직 변경 카드와 스키마 버전 검토가 필요하다.
- 기존 편집기 저장 형식에 assault 필드를 몰래 추가하거나 기존 피버 콘텐츠를 자동 재해석하지 않는다.
- 신규 편집기 지원은 별도 후속 트랙이다. 초기 콘텐츠는 버전이 있는 정적 데이터로 제공한다.
- 데이터 변경도 유효성·결정성·legacy 불변 테스트를 실행한다. 설정 파일이라는 이유로 검증을 생략하지 않는다.
- 프로필 후보값은 설정에만 두고 문서 예시나 테스트용 상수가 프로덕션의 두 번째 기본값이 되지 않게 한다.
- v0.2의 구조 제안을 기준으로 카드를 등록하되 §14의 미확정 밸런스 수치는 관련 카드 착수 전에 결정한다.

## 7. 답 공격 판정 계약

### 7.1 공격 하나, 시각 객체 둘

좌우 탄환은 하나의 pairId와 피해 결과를 공유한다. 각각을 독립 필수 타격 노트로 등록하여 선택하지 않은 탄환을 Miss로 처리하지 않는다.

```text
pending -> correct -> cancelled
pending -> wrong_locked -> impacted
pending -> timeout -> impacted
```

| 상황 | 처리 |
|---|---|
| 유효한 정답 펀치 | 정답 확정, 쌍 전체 무효화, 도착 피해 0 |
| 유효한 오답 펀치 | 오답 잠금, 방어 실패 표시, 도착 시 피해 1회 |
| 마감까지 미선택 | timeout 확정, 도착 시 피해 1회 |
| 양손 동시 입력 | 선택하지 않음. 남은 창에서 새 유효 동작으로 재시도 가능 |
| 잠금 이후 추가 입력 | 무시 |
| 무효화된 쌍의 도착/콜백 | 무시 |

- 선택 가능 창은 공격 도착 시각을 넘지 않는다.
- 오답 입력 순간 HP를 깎지 않는다. 도착 정산에서만 실제 피해를 적용한다.
- 양손 동시 입력의 허용 오차는 config 값으로 정의하고 아직 수치를 확정하지 않는다.
- 한 inputId는 최대 한 공격에만 귀속된다.
- 정답 여부와 박자 등급을 분리한다. 유효 창 안의 늦은 정답을 수학 오답으로 저장하지 않는다.
- 다음 스쿼트 성공이 이전 오답 피해를 취소하지 않는다.
- v0.3: 손-답 매핑(§15.1-A4), 판정 마감과 시각 도착의 분리 및 입력 지연 보정(§15.2-B6), 공격 중 일시정지 재개(§15.2-B8)를 따른다.

### 7.2 반복 보기 생성

- 초기에는 기존 문제 하나를 풀고 같은 정답값을 새 보기 쌍에서 반복 식별한다.
- 매 쌍에 정답은 정확히 하나만 둔다. 수치적으로 같은 오답을 배제한다.
- 정답 위치와 오답 조합을 바꾸되 항상 좌우 교대하는 정답 패턴을 강제하지 않는다.
- 시드 기반 생성을 지원하여 동일 조건 재현과 자동 테스트가 가능하게 한다.
- 문제 하나의 네 번 정답 타격을 네 문제 해결로 기록하지 않는다.
- 수식형 보기 생성과 검증은 초기 숫자형 이후 별도 카드로 진행한다.

## 8. 펀치·스쿼트·점프 입력 계약

### 8.1 펀치

```text
준비 -> 타격 진입 -> 이벤트 1회 -> 회수 대기 -> 준비
```

- 좌우 손 준비 상태를 각각 유지한다.
- pair 전환 시 준비 상태를 강제로 초기화하지 않는다.
- 정지한 손 또는 추적 복구 직후 손이 공격을 연속 선택하지 않게 한다.
- 회수 임계값과 타격 임계값을 분리하여 경계 떨림을 억제한다.
- 기존 커서 좌표·미러링을 유지하고 신규 경로에서 다시 반전하지 않는다.
- v0.3: 2D 카메라에서 정면(z축) 펀치는 신뢰할 수 없다. "펀치"의 화면상 판정 정의는 §15.1-A3을 따른다.
- **v0.4 개편 (#726, #730)**:
  - 2D 정적 사각 박스 의존도를 완전히 폐기하고, 화면 속 **메카 졸라맨 아바타의 팔 뻗기 방향 벡터($\vec{v}.x$)와 신전율($Ratio$)**을 기준으로 펀치를 판정한다.
  - **동적 찌르기(Stroke 엣지 트리거)**: 신전율 $60\% \rightarrow 80\%$ 도달 순간에만 1회 발화하며, 미리 뻗은 채 정지해 있는 손은 무효 처리한다.
  - **연타/잽 회수 완화**: $65\%$ 이하로만 팔을 살짝 당겨도 즉시 재장전되어 경쾌한 연속 타격이 가능하다.
  - **조기 타격(Early Miss, #730)**: 정박보다 너무 이른 시점($<-250\text{ms}$)에 들어온 펀치는 잠금/피해 없이 Miss로만 처리하고 유효 시간 내 재타격을 허용한다.

### 8.2 스쿼트

```text
직립 보정 -> 낮아짐 -> 판정 구간의 안전 자세 확인 -> 직립 복귀
```

- 보정 기준과 현재 좌표의 단위를 일치시킨다.
- 스쿼트 성공은 해당 공격의 판정 구간에서 안전 자세를 만족했는지로 판단한다.
- 다음 공격에는 직립 복귀가 필요하다. 계속 앉아 있는 상태로 연속 성공하지 않는다.
- 깊은 스쿼트를 강제하지 않고 사용자 가동 범위에 맞춘다.
- 공격 실패 피해 역시 attackId당 한 번만 적용한다.

### 8.3 점프 및 폴백

- 초기 접근전은 펀치/스쿼트 중심이며 점프는 근접 결전 단계에서 추가한다.
- 실제 점프 성공을 캐릭터 자동 공격으로 연결하는 안을 우선한다. 실제 점프 중 펀치를 강제하지 않는다.
- 저충격 대체 동작을 제공하고 수학 타격 집계는 동일 규칙으로 유지한다.
- 키보드/터치는 같은 동작 계약을 사용한다. 한 키 유지나 자동 반복으로 여러 공격을 처리하지 않는다.
- 동작 종류와 맞지 않는 폴백 입력이 다른 판정기를 우회하지 않게 한다.

## 9. HP·보상·라운드 정산

### 9.1 단일 자원 소유자

플레이어 HP는 기존 BattleState, 보스 HP는 기존 BossController를 재사용하는 안을 우선한다. 신규 컨트롤러에 별도 HP 사본을 만들어 권위가 둘이 되지 않게 한다.

자원을 변경하는 요청은 신규 정산 경로 한 곳으로 모은다. 기존 onWrong처럼 답 통계와 피해가 결합된 API를 중복 호출하지 않는다. 초기화 시 설정 주입 가능 여부를 먼저 확인하고, 전역 DEFAULT_CONFIG를 신규 모드 때문에 변경하지 않는다.

### 9.2 즉시 정산과 라운드 정산 분리

| 시점 | 반영 |
|---|---|
| 답 선택 확정 | 정답/오답 타격·콤보 기록 |
| 답 선택 마감 | 미선택 기록 |
| 공격 도착 | 실제 HP 피해, 한 번만 적용 |
| 회피 확정 | 회피 결과 기록 |
| 전체 공격 종료 | 불변 라운드 요약 생성, 완료 문제 수 +1 |
| 사망/강제 종료 | 중단 요약 생성, 완료 문제 수 증가 없음 |

라운드 요약의 피해 합계는 이미 적용된 피해의 기록이다. 요약을 처리하면서 HP를 다시 차감하지 않는다.

### 9.3 기존 resolver와의 경계

- BeatRoundResolver.resolveRound를 pair마다 호출하지 않는다.
- 복합 결과를 억지로 단일 correct/wrong으로 축약하지 않는다.
- 신규 RoundSummary를 별도로 정의하고, 진행 시스템은 완료 여부·완료 문제 수·생존 여부를 받는다.
- 기존 BattleState의 correctCount를 반복 타격 카운터로 재정의하지 않는다. 신규 통계는 별도 결과 모델을 소유한다.

### 9.4 보상 단계

**핵심 시제품**에서는 HP·타격·회피·접근만 검증한다. 마나/미니언/별가루 지급과 기존 최고기록·성장 저장은 하지 않으며, 해당 미연결 HUD도 활성 기능처럼 표시하지 않는다.

**보상 연결 단계**에서는 문제당 보상 상한과 정답 비율 기반 지급안을 별도 승인한다. 다음은 미확정이다.

- 마나 지급 시점·상한·반올림 방식과 스펠의 접근전 역할.
- 미니언·수호신 성장 유지 여부 및 신규 결전 참여 방식.
- 별 수집 제거 이후 별가루 유지·대체·미사용 정책.

가짜 별 판정을 만들어 기존 보상 경로를 호출하지 않는다. 공격 수가 증가했다는 이유로 기존 +25 마나 보상을 타격마다 적용하지 않는다.

## 10. 접근 진행도와 근접 결전

### 10.1 접근

```text
접근 진행도 = 완료 라운드 수 / 목표 라운드 수
```

- 목표 라운드는 초기 검증값 10이며 모드 전용 설정으로 둔다.
- 라운드 완료 시 정답률과 무관하게 전진한다. 오답으로 같은 위치에 무한 대기하지 않는다.
- 실제 사용자는 제자리에서 운동한다. 배경·보스 크기·거리 변화로 접근을 표현한다.
- HP 0이 진행도 증가나 결전 진입보다 우선한다.
- 마지막 라운드 정산 후 다음 문제를 생성하지 않는다.
- 결전 인계는 세션당 한 번이며 HP·모드·규칙 버전·집계 스냅샷을 유지한다.

### 10.2 결전

```text
약점 펀치 -> 가로 공격 스쿼트 -> 약점 펀치
 -> 바닥 충격파 점프/대체 -> 큰 빈틈 연타
```

- 예고·입력창·결과·복귀를 갖춘 명시적 패턴으로 구성한다.
- 새 결전 컨트롤러가 패턴 진행을 소유하고 정산기를 통해서만 피해를 적용한다.
- 기존 피버·보스 자동 공격·미니언 포격은 자동 활성화하지 않는다.
- 보스 HP·펀치 피해·허용 실패 수·목표 결전 시간은 신규 프로필에서 함께 조정한다.
- 보스와 플레이어가 같은 처리 시점에 모두 HP 0이 되면 플레이어 사망을 우선하는 안을 적용한다.
- 점프 대신 저충격 동작을 선택한 경우의 기록 비교 조건은 명시한다.
- 피버를 결전 명칭으로 사용할지 결전 내 강화 상태로 둘지는 아직 미확정이다.

## 11. 렌더링·효과·결과 기록

### 11.1 표시 원칙

- 보스 양손 위치를 발사 기준으로 사용하되 투영·판정 앵커는 공용 기능과 일치시킨다.
- 좌우 답을 연결한 시각 표현으로 하나의 공격 쌍임을 알린다.
- 정답 시 양쪽 공격이 함께 소멸하고, 오답 시 방어 실패 예고 후 도착 시 피격 효과를 재생한다.
- 화면 흔들림·파편이 문제와 다음 답을 가리지 않게 한다.
- 읽기 전용 스냅샷에 취소/피격 상태를 명시한다. 취소된 탄환을 두 번째 hit나 miss로 꾸미지 않는다.
- 기존 MotionNoteTimeline을 재사용할 경우 매 pair마다 loadNotes로 전체 시퀀스를 초기화하지 않는다.

### 11.2 결과 항목

- 완료 문제 수, 시도한 답 공격 수, 정답 타격 수, 오답 타격 수, 미선택 수.
- 최대 타격 콤보, 리듬 정확도, 회피 성공/실패 수.
- 실제 활성 플레이 시간, 남은 HP, 도달 진행도, 결전 결과.
- 중도 종료 여부, 입력/접근성 프로필, 규칙 버전.

기존 결과 화면의 시간·운동 횟수 전달 경로를 그대로 신뢰하지 않고 신규 실측 통계를 연결한다. 구현되지 않은 수치를 임의 상수로 표시하지 않는다.

### 11.3 저장과 순위

- 초기 테스트 세션은 기존 최고기록·성장 저장을 갱신하지 않는다.
- 정식 신규 기록은 mode/rulesVersion/profile을 포함해 legacy와 분리한다.
- 비교 조건에 문제 난도, 템포, 공격 기회 수, 문제 형식을 포함한다.
- 순위 우선순위는 정답 타격 수, 오답 수, 리듬 정확도 순을 후보로 하되 별도 확정한다.
- 숫자 반복 식별 4회와 서로 다른 수식 계산 4회를 같은 학습 성취로 기록하지 않는다.

## 12. 단계별 작업 묶음

아래는 구현 순서 제안이다. 각 묶음은 여러 카드로 나눌 수 있으며, 하나의 카드에서 여러 레이어를 동시에 수정하는 승인이 아니다. 카드별 src/config 변경은 최대 3개 파일로 제한하고 tests와 문서 범위를 별도로 기록한다.

| 순서 | 작업 묶음 | 주요 책임 | 완료 조건 |
|---|---|---|---|
| 1 | 현행 사양 대조·결정 기록 | 문서 | 문서/코드 차이, 유지/대체 범위 확정 |
| 2 | 신규 데이터 계약·설정 | types/config 각각 분리 | 한 문제에 다중 공격 표현, 기존 기본값 불변 |
| 3 | 신규 모드 실행 경계 | core 연결 카드로 분리 | 기존/신규 배타 실행 및 종료 검증 |
| 4 | 문제 등장·읽기 시간 | game / render 별도 카드 | 연출 제외 8박, TTS 실패에도 진행 |
| 5 | 답 한 쌍 판정·정산 | game | 정답 취소, 오답 도착 피해 정확히 1회 |
| 6 | 회수 기반 펀치 입력 | motion/input | 손 유지 자동 선택 방지 |
| 7 | 스쿼트 검증·회피 판정 | motion / game 별도 카드 | 좌표 일관성, 복귀 필요, 한 번 정산 |
| 8 | 반복 공격 시퀀스 | game | 여러 pair와 squat, 라운드 정산 1회 |
| 9 | 신규 시각 연결 | render / UI 별도 카드 | 투척·양손 탄환·무효화·피격 표시 |
| 10 | 접근·사망·인계 | game / core 별도 카드 | 사망 우선, 마지막 인계 1회 |
| 11 | 근접 패턴 | game, 동작별 카드 | 펀치/회피/점프 순차 검증 |
| 12 | 보상·결과·저장 | game / UI / storage 별도 카드 | 중복 없음, 기록 분리 |
| 13 | 실기기 검증·기본값 전환 | QA 후 별도 전환 카드 | 읽기·인식·피로·회귀 기준 통과 |
| 14 | 수식형 답·랭킹 확장 | question / 기록 별도 카드 | 안전 평가·정답 유일성·동일 조건 비교 |

각 구현 카드는 Baseline -> Red 확인 -> 최소 구현 -> Green -> 전체 테스트/빌드 순서를 따른다. 승인 범위를 넘는 수정은 별도 카드로 분리한다. 완료 기록, 이슈 코멘트, 서버 안내는 실제 승인된 카드 완료 시 수행한다. 문서 작성만으로 구현 완료나 테스트 통과를 기록하지 않는다.

### 13.1 대표 통합 시나리오

```text
문제 투척 -> 고정 후 8박
 -> 정답 펀치 -> 양쪽 무효화
 -> 스쿼트 성공
 -> 오답 펀치 -> 도착 피해 1회
 -> 스쿼트 실패 -> 해당 공격 피해 1회
 -> 정답 펀치 -> 양쪽 무효화
 -> 스쿼트 성공
 -> 라운드 요약 1회 -> 완료 문제 수 +1 -> 접근
```

이 시나리오의 피해·정답·회피 횟수를 자동 테스트에서 확인한다. 중간 일시정지와 재시작 변형도 별도로 검증한다.

### 13.2 실기기 확인

- 데스크톱/모바일에서 답 가독성, 보스 손과 판정 위치 일치, 화면 이탈 안내를 확인한다.
- 실제 읽기 시간 부족, 펀치 미인식/중복, 스쿼트 복귀 실패, 팔·하체 피로를 기록한다.
- 정답·오답과 인식 실패를 구분해 관찰한다. 단위 테스트 통과만으로 타격감을 검증했다고 주장하지 않는다.
- 측정 전 운동 효과 배율이나 인식 지연 수치를 확정 수치로 제시하지 않는다.
